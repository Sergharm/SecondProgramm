# Введение

При выполнении неизвестной программы её фактическое поведение зависит от аргументов, среды и действий пользователя. Одного просмотра файла недостаточно, чтобы установить, обращается ли процесс к сети и какие операции с сокетами он выполняет. При этом запуск в обычном пользовательском окружении опасен для данных и сетевых ресурсов. Для учебного эксперимента нужны воспроизводимые входные данные, контролируемая среда и журнал наблюдений.

Цель работы — разработать на C++ учебный прототип изолированного динамического анализа программ под Linux с регистрацией операций TCP- и UDP-сокетов. Для достижения цели требуется сопоставить способы изоляции, выделить компоненты приложения, реализовать безопасный сценарий запуска, преобразовать трассировку в записи событий и проверить их на собственных образцах.

Объект исследования — выполнение программ в Linux. Предмет исследования — методы изоляции процессов и регистрации их сетевых системных вызовов. Практическая значимость заключается в возможности связать код сетевого приложения с наблюдаемыми вызовами ядра, сопоставить успешный и ошибочный результаты и сохранить воспроизводимый текстовый отчёт.

# 1 Анализ предметной области

## 1.1 Понятие программной песочницы

Песочницей называют среду выполнения, которая ограничивает видимые исследуемому процессу ресурсы. Для наблюдения к среде добавляют инструменты регистрации поведения. В учебном сценарии граница доступа задаёт наблюдаемое окружение. Сеть содержит loopback, доступ к файловой системе ограничен необходимыми библиотеками, а перечень программ известен до запуска.

## 1.2 Статический и динамический анализ программ

Статический анализ исследует свойства артефакта до выполнения. Например, первые четыре байта позволяют распознать сигнатуру ELF. Динамический анализ регистрирует действия за конкретный сеанс исполнения. Успешный `connect` свидетельствует об установлении конкретного соединения. Отсутствие вызова в одном сеансе само по себе не исключает его при другом входе или в иной среде.

## 1.3 Эмуляция, виртуализация и изоляция

Эмуляция воспроизводит поведение целевой машины либо программного интерфейса. В качестве примера QEMU описывает модель процессора, памяти и устройств для запуска гостевой ОС [1]. Виртуализация предоставляет гостевой системе собственное окружение виртуальной машины. VirtualBox позволяет запустить Linux как гостевую систему [2]. Изоляция средствами ядра Linux ограничивает представление о ресурсах для выбранных процессов. Динамическое наблюдение получает сведения о конкретном выполнении. В проекте Kali Linux работает в VirtualBox, Bubblewrap подготавливает изоляцию внутри Linux, а strace регистрирует системные вызовы.

## 1.4 Методы изоляции процессов в Linux

Пространства имён задают разное представление о сетевом стеке, процессах и подключённых компонентах файловой системы [3]. Сетевое пространство имён может содержать собственные интерфейсы и маршруты. Пространство монтирования определяет видимые точки монтирования. Bubblewrap формирует ограниченное окружение при помощи соответствующих параметров [4]. Для прототипа важны раздельные пространства имён, отсутствие монтирования домашних и общих каталогов, чтение библиотек и отказ при ошибке инициализации. Пространства имён используют ядро Linux, на котором работает приложение. Безопасность проекта опирается также на выполнение только собственного набора образцов.

## 1.5 Системные вызовы Linux

Системный вызов передаёт запрос приложения ядру. Имя библиотечной функции может отличаться от имени системного вызова в трассе. strace отображает параметры и возвращаемые значения наблюдаемых вызовов [5]. Для одной операции `connect` это может быть адрес назначения и возврат `0`, либо `-1` и имя ошибки. Для полноты интерпретации учитывают архитектуру, набор вызовов и представление дескрипторов конкретной версией трассировщика.

## 1.6 Сетевые сокеты TCP и UDP

Сокет представляет конечную точку обмена, доступную приложению по файловому дескриптору. TCP предоставляет ориентированный на соединение поток байтов. Типовой сервер связывает сокет с адресом через `bind`, переводит его в режим ожидания через `listen` и получает соединение через `accept` [6]. UDP передаёт независимые датаграммы. Тест использует `sendto` для адресной отправки и `recvfrom` для приёма [7]. Обе программы работают с IPv4 loopback и позволяют ядру назначить порт. Трассировка уровня системных вызовов показывает обращения процесса к ядру. Для анализа пакетов необходим самостоятельный источник данных о сетевом трафике.

## 1.7 Анализ функциональных возможностей ANY.RUN

ANY.RUN описывает облачную интерактивную среду, в которой оператор взаимодействует с виртуальной машиной из браузера. Документация указывает дерево процессов, представление сетевых соединений, DNS и HTTP, средства изучения файловых событий, экспорт HTML и JSON и получение сетевого захвата [8, 9]. Для LinuxSandbox из этого подхода заимствована идея связывать наблюдаемые операции с контекстом выполнения и сохранять результаты. Сведения об аналоге основаны на официальном описании сервиса.

## 1.8 Обзор существующих решений

Cuckoo Sandbox в документации ветки 2.0.7 описывает данные наблюдения за процессами, файловые результаты, дамп PCAP и отчёты JSON и HTML [10]. Это пример пакетной организации артефактов. Для локального инструмента UNIX-систем strace служит источником трассы и диагностики [5]. Bubblewrap решает задачу подготовки среды Linux [4]. В LinuxSandbox эти инструменты вызываются по разным причинам и объединены собственным прикладным кодом.

## 1.10 Постановка задачи

Требуется реализовать консольный прототип для локального эксперимента. Вход — путь к файлу, который можно изучить до исполнения. Запуск разрешается для TCP- и UDP-образцов конкретной сборки. Выход — характеристика результата сеанса, события и текстовый отчёт. Проверка должна включать допуск, доступность изоляции, корректную классификацию наблюдаемых операций и обработку отказов.

# 2 Проектирование программного обеспечения

## 2.1 Обоснование выбора C++

C++ позволяет вызывать интерфейсы Linux и POSIX напрямую, организуя при этом владение дескрипторами через RAII. Возможности C++17 `std::filesystem`, `std::optional` и `std::string_view` позволяют явно представлять путь, отсутствие результата и представление байтов без лишней копии.

## 2.2 Обоснование выбора Linux

Linux предоставляет пространства имён и системный интерфейс UNIX-процессов, с которыми работают Bubblewrap и strace. Целевые исследования относятся к программам Linux. На проверяемой платформе используется архитектура x86_64, что определяет формат собственных ELF-образцов и расположение основных библиотек.

## 2.3 Выбор среды разработки

Kali Linux x86_64 используется в VirtualBox. Visual Studio Code предназначен для работы с многофайловым кодом и локальным терминалом. Git хранит исходники, сборочные инструкции и историю изменений. Программные отчёты и материалы с персональными данными хранят локально.

## 2.4 Выбор системы сборки

CMake описывает цели приложения и двух тестов, общий стандарт языка и диагностические предупреждения компилятора. Отдельная команда создаёт заголовок из байтов готовых тестов. Зависимости сборки обеспечивают пересоздание заголовка после изменения соответствующих целей [11].

## 2.5 Выбор средств изоляции

Bubblewrap выбран как поставщик изолированного пространства выполнения. Приложение описывает аргументы монтирования, копию образца, окружение и ограничения привилегий. Использование внешней утилиты упрощает отделение политики изоляции от кода запуска.

## 2.6 Выбор средств мониторинга

strace обеспечивает трассировку системных вызовов готового исполняемого файла, разбор сетевых операций и декодирование дескрипторов [5]. Формат анализируемых записей остаётся текстовым. Точность структуризации зависит от формы строк и от доступных аргументов.

## 2.7 Функциональные требования

Система должна принимать команды, выбирать читаемый обычный файл, показывать его свойства, проверять допуск образца и запускать его в пределах регламентированного времени. После анализа требуется обеспечить просмотр результата, журнала и сохранение TXT.

## 2.8 Нефункциональные требования

Требуются локальная сборка, понятные сообщения, работа от обычного пользователя, независимость ядра от интерфейса и отказ при недоступной изоляции. Ограничение времени и чтения трассы сокращает объём обрабатываемого результата. В отчёте отмечаются неполные поля и ошибки.

`FileInfo` объединяет путь, размер, признак исполнения и строку типа. `Analysis` объединяет статус, вектор `Event` и диагностику. ## 2.12 Проектирование пользовательского интерфейса

Консольное меню предоставляет команды от 0 до 6. После выбора файла путь виден в меню. Анализ предшествует действиям просмотра сетевых событий и сохранения. Ошибка отображается в том же сеансе, поэтому пользователь может повторить ввод. Развитие графического интерфейса Qt 6 рассматривается в перспективной схеме.

## 2.13 Проектирование форматов журналов и отчётов

Журнал состоит из строк со временем и сообщением. Запись события содержит поля PID, операция, протокол, IP, порт, исход и возвращаемое значение. TXT включает заголовок, метаданные сеанса, табличный блок с разделителем табуляции и журнал. Для отсутствующих данных при сохранении используется дефис.

# 3 Реализация программного обеспечения

## 3.1 Организация исходного кода

В `src/` располагаются точка входа и шесть модулей. В `include/` описаны классы и передаваемые структуры, в `tests/` — два контрольных примера. В `cmake/` находится формирование `AllowedTests.h`, который возникает в сборочной конфигурации.

## 3.2 Реализация точки входа программы

`main()` вычисляет расположение приложения по `/proc/self/exe`, создаёт `Sandbox` и запускает `ConsoleUI::run()`. При исключении на верхнем уровне сообщение выводится в `stderr`, а программа возвращает 1.

## 3.3 Реализация пользовательского интерфейса

`ConsoleUI` хранит ссылку на `Sandbox`. Команда читается `std::getline`, а внешние пробелы, табуляция и `CR` удаляются из команды. При исключении пункт показывает сообщение об ошибке. Команда 0 или конец ввода завершает сеанс.

## 3.4 Реализация обработки исследуемого файла

`Sandbox::select` канонизирует путь, проверяет читаемость и тип файла. `fileInfo` получает размер и читает сигнатуру ELF. Перед запуском `verifyFile` поблочно сравнивает содержимое с эталоном из сборки. В `ProcessManager` передаются встроенные байты, поэтому запуск относится к учтённому образцу.

## 3.5 Реализация управления процессами

`ProcessManager` создаёт временные объекты memfd для передачи образца и получения вывода. Дочерняя ветвь `fork()` настраивает стандартные потоки и выполняет `execve`. Родитель опрашивает статус через `waitpid` с `WNOHANG` и ограничивает ожидание пятью секундами. По тайм-ауту он отправляет `SIGKILL` управляемому процессу и ожидает его завершения.

## 3.6 Реализация механизмов изоляции

`IsolationManager` проверяет отсутствие повышенных привилегий и доступность внешних инструментов. Ему принадлежат параметры раздельных пространств имён, очищенного окружения, чтения библиотек, приватных `/proc` и `/dev` и чтения `/sample`. Каталоги проекта, домашний каталог и общие папки образцу не монтируются. Внешний обмен образцов отсутствует.

## 3.7 Реализация мониторинга системных вызовов

strace запускается внутри Bubblewrap с фильтром `%network`, отслеживанием потомков и декодированием дескрипторов. Трасса направляется в `stderr`, который читается из временного объекта после завершения. В анализ передаётся до 128 КиБ. Незавершённые и неразобранные строки могут попасть в диагностику.

## 3.8 Реализация мониторинга сетевых сокетов

`NetworkMonitor::parse` выделяет PID, имя вызова, аргументы и числовой результат регулярными выражениями. Протокол определяется по аннотации TCP/UDP, значению аргумента или ранее установленной связи PID и дескриптора. IP и порт извлекаются из структур адреса либо декодированной записи сокета. IPv6 учтён в шаблонах, а комплектные тесты используют IPv4.

## 3.9 Реализация формирования журналов

`Sandbox::log` помещает сообщение с локальной отметкой времени в вектор строк. Журнал живёт в течение сеанса. Для попытки анализа сохраняются статус и диагностика при их наличии.

## 3.10 Реализация формирования отчётов

`Sandbox::saveReport` строит текст по последнему анализу. `ReportManager::save` создаёт `reports/analysis-XXXXXX.txt` и записывает содержимое через файловый дескриптор. Сообщение текущего сохранения добавляется в журнал после записи и появится только в последующих отчётах данного сеанса.

## 3.11 Обработка ошибок и освобождение ресурсов

Доступ к дескрипторам обёрнут в `FileDescriptor`, который закрывает их при выходе из области видимости. Операции чтения и записи обрабатывают `EINTR`. При ошибке записи отчёта неполный файл удаляется. Ошибки подготовки анализа превращаются в статус отказа, ошибки меню выводятся в консоли.
